# סיכום המערכת - טופס קליטת עובד (שתילים)

מסמך התמצאות למי שנכנס לפרויקט מחדש. לפרטי מימוש עדכניים - לקרוא את הקוד; המסמך הזה
נותן מפה, לא תיעוד API מלא.

## מה המערכת עושה

אפליקציית Next.js עצמאית שמחליפה טופס Fillout לקליטת תקני עובדים במוסדות רשת
"מיוחדים בחינוך" / "שתילים". כל הנתונים חיים ב-Airtable (בסיס תשפ"ז) - האפליקציה
היא שכבת UI + לוגיקת חישוב מעל הבסיס, כמעט בלי מסד נתונים משלה.

שני משטחים עיקריים:

1. **פורטל מוסד** (`/form/[token]`) - עמוד נחיתה למוסד ספציפי (מזוהה לפי טוקן ב-URL,
   לא לפי התחברות), עם 4 כרטיסי מודול.
2. **אשף קליטת תקן** (Wizard, 4 שלבים) - עובד → תפקיד → מערכת שעות → סיכום. פעיל גם
   ב"עריכת תקן" וגם ב"טעינה משנה קודמת".

## Stack טכני

- Next.js 14 (App Router), React 18, TypeScript, Tailwind.
- Zod לוולידציה, pino ללוגים.
- `googleapis` - הפקת מסמכי "בקשת תשלום" ב-Google Docs לתקני חשבונית (Drive API,
  OAuth2 כמשתמש אמיתי - ראו "הפקת בקשת תשלום" למטה).
- Vitest ליחידות - בעיקר `src/lib/schedule/*` ולוגיקת חישוב טהורה (`*.test.ts` לצד
  כל קובץ לוגיקה).
- ריצה מקומית: `npm run dev` על פורט 3010 (ראו [[shtilim-dev-workflow]] - אל תריצו
  build כשה-dev server רץ).
- אין התחברות משתמשים; גישה נשלטת ע"י טוקן פר-מוסד (ראו "אבטחה" למטה).

## זרימת המשתמש

### פורטל מוסד (`InstitutionPortal.tsx`)

4 כרטיסים ב-`/form/[token]`:

| כרטיס | נתיב | סטטוס |
|---|---|---|
| ניהול תקנים | `/form/[token]/positions` | פעיל - צפייה/עריכה/מחיקה/הוספה של תקנים |
| תקציב התחלתי | `/form/[token]/budget` | פעיל - צפייה בלבד בנתוני התקציב |
| ניהול תקני חשבונית | `/form/[token]/invoice` | פעיל - הקצאה שנתית ודיווח חודשי (ראו למטה) |
| תיק אישי לעובד | `/form/[token]/personnel` | בפיתוח |

"ניהול תקנים" הוא `InstitutionDashboard.tsx` - טבלה עם סינון לפי סוג עמודה, מיון,
וכפתורי הוספה/עריכה שפותחים את ה-Wizard.

### אשף קליטה (`Wizard.tsx` + `src/components/steps/*`)

4 שלבים (`src/lib/steps.ts`):

1. **עובד** (`EmployeeStep`) - חיפוש עובד קיים לפי ת.ז. או הוספת עובד חדש. שדות: שם,
   ת.ז., כתובת, מייל, טלפון (חובה, ולידציית טלפון ישראלי), מגדר, מצב משפחתי, ילדים
   מתחת 14, תאריך לידה, תאריך תחילת חוזה, משרת אב, העסקה 12 שעות, מסמכי נוער/תפקיד
   (העלאה מותנית - ראו [[shtilim-document-uploads]]). תיבת סימון "עובד/ת ללא תעודת
   זהות ישראלית" מחליפה את ולידציית ה-checksum בפורמט חופשי למספר דרכון/זיהוי זר
   (`isValidForeignId`, `src/lib/validation/foreignId.ts`); אין שדה איירטייבל נפרד -
   העובדה נגזרת מחדש מפורמט ה-tz בכל טעינה. התאמת-עובד בין תקנים (דה-דופ, דגל 12
   שעות) עוברת דרך `buildTzExactMatchFormula` (`src/lib/airtable/tzMatch.ts`), שמפריד
   מסלול ספרות-ישראלי ממסלול זיהוי-זר כדי שלא יתאפשר collision בין שני זיהויים זרים
   בעלי אותה סדרת ספרות.
2. **תפקיד** (`RoleStep`) - בחירת תקן מתוך תקציב המוסד (סמל → תפקיד → קטגוריה),
   תת-תפקיד (כשרלוונטי), גמולים, תפקידים נוספים, אישור לנדברג (מטפל/ת רגשית/אומנות),
   שדות שכר/דירוג לתצוגה בלבד.
3. **מערכת שעות** (`ScheduleStep`) - הזנת שעות שבועיות (עד 3 משמרות ליום, sun-fri
   + מוצ"ש רגיל בלבד), הפסקות, חישובי אופק, בדיקות תקרה/חפיפה/נוער - כל הלוגיקה
   הכבדה נמצאת כאן (ראו "לוגיקת ליבה" למטה).
4. **סיכום** (`SummaryStep`) - תצוגת כל הנתונים + שליחה (`POST /api/submit`).

זרימות נוספות שמזינות את ה-Wizard במצב שונה:

- **עריכת תקן קיים**: `mode="edit"`, נטען דרך `loadPosition.ts`, מתחיל בשלב "מערכת
  שעות" (לא "עובד"), אין חזרה לשלב עובד. משלב מערכת שעות ניתן לעבור גם לשלב "תפקיד"
  (כפתור "עדכון גמולים ותפקידים") - שם התפקיד/הסמל עצמם נעולים, וניתן לעדכן רק
  גמולים/תפקידים נוספים/תת-תפקיד. ראו [[feature-edit-position]],
  [[feature-edit-gemulim-roles]].
- **טעינה משנה קודמת (תשפ"ו)**: `/form/from-prev-year/[id]` - טוען שורת תקן משנה
  קודמת (`loadPrevYearFull.ts`), מציג סיכום שנה קודמת, מדגיש שדות עובד חסרים. ראו
  [[feature-from-prev-year-prefill]].
- **תקן חדש לעובד קיים משנה קודמת**: `/form/from-prev-year-new/[id]`
  (`loadPrevYearForNewRole.ts`) - רק עובד+מוסד נטענים, השאר מלא מאפס. ראו
  [[feature-new-role-from-prev-year]].

### מודול תקני חשבונית (`/form/[token]/invoice/*`)

טיפול נפרד לגמרי מהאשף הרגיל - תקן בקטגוריית "חשבונית" בתקציב **אינו** עובר דרך
ה-Wizard כלל (`HIDDEN_CATEGORIES` ב-`RoleStep.tsx` מסנן אותו מרשימת התפקידים), ואין
קשר 1:1 בין תקן לעובד: תקן חשבונית בודד יכול להיות מקושר למספר עובדים במקביל, כל
אחד עם חלוקת שעות ותעריף שעתי משלו מתוך "עוגה" תקציבית משותפת. שלושה מסכים:

1. **`InvoiceDashboard.tsx`** (`/form/[token]/invoice`) - רשימת שורות התקציב
   בקטגוריית חשבונית של המוסד, עם מס' עובדים מוקצים ומצב הקצאה.
2. **`AllocationScreen.tsx`** (`/form/[token]/invoice/[budgetRowId]`) - "ניהול
   תקציב": הוספת/עריכת/הסרת עובדים מוקצים לתקן - חיפוש עובד קיים לפי ת.ז. או
   יצירת עובד חדש (אותם API routes כמו `EmployeeStep`), תת-תפקיד + מסמך רישיון
   (reuse מדויק של `SUB_ROLE_DOC_FIELDS`/`DocUpload` הקיימים מתפקידי פרא), שעות
   מוקצות ותעריף שעתי מוסכם. כפתור "סיום הקצאה שנתית" (stub).
3. **`MonthlyReportScreen.tsx`** (`/form/[token]/invoice/[budgetRowId]/report`) -
   דיווח שעות בפועל + תעריף + מס' חשבונית לכל עובד מוקצה בחודש נבחר (ברירת מחדל:
   החודש הקודם), עם העלאת חשבונית/דרישת תשלום לכל דיווח - **ניתנת להחלפה** כל
   עוד החודש בעריכה (לא נעול): `/api/invoice/upload-report-doc` מנקה קודם את
   שדה הצירוף הקיים (`updateRecord` לערך ריק) ורק אז מעלה את הקובץ החדש, כי
   ה-endpoint של Airtable ל-attachment **מוסיף** לרשימה הקיימת ולא מחליף
   אותה - בלי הניקוי, הקובץ הישן (לא החדש) היה נשאר זה שנקרא בפועל בהפקת
   המסמך. אותו route בודק נעילת חודש בעצמו (409), לא רק ה-UI. כפתור "סיום דיווח חודשי
   ושליחה" דורש כתובת מייל (מוזנת מחדש בכל סיום, לא שדה קבוע) - מסמן checkbox,
   מפיק מסמך "בקשת תשלום" (קישורים למסמך/לתיקייה/ל-PDF המאוחד מוצגים מיד ב-UI
   ונשמרים לטעינות הבאות), ושולח אותם במייל דרך Make. **נועל את החודש לחלוטין**
   לאחר מכן (v1: אין פתיחה מחדש) - ראו "נעילת חודש" למטה.

כללי הוולידציה (נאכפים גם בלקוח וגם ב-live re-check בשרת, כמו `budgetCheck.ts`):
"שעות לניצול" היא **מכסה חודשית** (reuse של השדה הקיים `סך שעות בתקציב`, לא שדה
נפרד - מתאפסת ונבדקת מחדש כל חודש, לא מצטברת על פני השנה). תעריף שעתי מקסימלי =
תעריף חודשי ÷ שעות לניצול (formula ב-Airtable). בהקצאה: סה"כ שעות מוקצות לכלל
העובדים ≤ המכסה, תעריף מוסכם לכל עובד ≤ המקסימלי. בדיווח חודשי: רק סה"כ שעות
מדווחות (כלל העובדים יחד) לחודש נתון ≤ המכסה - מותר לעובד בודד לדווח יותר שעות
ממה שהוקצה לו אישית, אין בדיקה פר-עובד על שעות. תעריף מדווח ≤ התעריף המוסכם של
אותו עובד. מספר עוסק מוסכם (`vatNumber`, על העובד) מאומת כ-9 ספרות בדיוק, גם
בשרת וגם ב-UI. "סיום הקצאה שנתית" הוא **stub בלבד** (checkbox). "סיום דיווח
חודשי" **כן** מפיק מסמך אמיתי - ראו "הפקת בקשת תשלום" למטה. הפקת המסמך קודמת
לסימון ה-checkbox: כשל בהפקה **לא** נועל את החודש (אפשר לנסות "סיום דיווח"
שוב) - ראו "נעילת חודש" למטה.

**נעילת חודש (v1, מלאה, בלי פתיחה מחדש):** ברגע ש-`monthlyTransferDocGenerated`
מסומן (checkbox על כל שורות הדיווח של אותו חודש+תקן), אין דרך לדווח/לערוך
מחדש לאותו חודש - נאכף גם ב-`POST /api/invoice/reports` (409) וגם ב-
`finish-report` (409 אם כבר סומן), וגם ב-UI (שורות נעולות, כפתור עריכה/סיום
מוסתרים, באנר "נעל" מוצג במקומם). זו החלטת מוצר מפורשת (v1) - אין עדיין דרך
לתקן חודש שכבר "יצא". **סדר הפעולות ב-`finish-report` קריטי בגלל זה**: המסמך
מופק **קודם**, והנעילה (וסימון checkbox) קורית **רק אחרי** שההפקה הצליחה
ונשמרה - אם ההפקה נכשלת, החודש נשאר פתוח ואפשר לנסות "סיום דיווח" שוב.

**עובד לא פעיל בתקן (`INVOICE_POSITION_FIELDS.inactive`, checkbox "לא פעיל"):**
מחיקת הקצאה חסומה כשקיימים דיווחים חודשיים מקושרים (409 ב-DELETE), כדי לא לאבד
היסטוריה - אבל עובד יכול להפוך ללא פעיל באמצע השנה בלי שהחלק שלו ימשיך "לתפוס"
מהמכסה החודשית המשותפת של התקן קדימה. `allocatedHours` הוא החלק הקבוע של העובד
מתוך המכסה החודשית (לא סכום מצטבר על פני השנה - ראו "כללי הוולידציה" למעלה),
כך שסימון "לא פעיל" (`setPositionActive` ב-`positions.ts`, כפתור ב-
`AllocationScreen`) מאפס אותו לגמרי - היתרה משתחררת חזרה למאגר דרך ה-rollup
הקיים (`BUDGET_FIELDS.totalAllocatedHours`), בלי צורך בלוגיקת סינון נפרדת
בבדיקות המכסה. דיווחים חודשיים היסטוריים לא נוגעים בהם. דיווח חודשי חדש ועריכת
שעות/תעריף חסומים (409) כל עוד ההקצאה לא פעילה. הפעלה מחדש לא משחזרת שעות
אוטומטית - מקצים ידנית מחדש אם צריך.

מודל הנתונים: `src/lib/invoice/{budget,positions,reports,budgetCheck}.ts`. שתי
טבלאות Airtable חדשות (ראו טבלה למטה) - עובד אחד מקושר תחת שורת תקציב חדשה תמיד
דרך רשומת "תקני חשבונית" נפרדת, **לא** דרך "תקנים פעילים" (שם יש אופק/הפסקות/לוח
צלצולים שלא רלוונטיים). סינון לפי תקן/מוסד נעשה ב-memory ולא ב-`filterByFormula`
כשמדובר בהתאמת record id על שדה `multipleRecordLinks` - ARRAYJOIN על שדה כזה
מחזיר את שם הרשומה המקושרת, לא את מזהה הרשומה, כך שאין דרך לסנן לפי id ישירות
בנוסחת Airtable על שדה כזה (הטבלאות קטנות, אז זה זול). כמו כן, תגובת
`createRecord`/`updateRecord` (`client.ts`) **אינה** מוחזרת עם `returnFieldsByFieldId`
(רק GET/list מבקשים את זה) - אסור למפות אותה ישירות לפי מזהי שדה; יש לבנות את
האובייקט המוחזר מהפרמטרים הידועים או לשלוף מחדש עם `getRecord`.

#### הפקת "בקשת תשלום" בגוגל דוקס

`src/lib/invoice/paymentRequestDoc.ts`: `buildPaymentRequestHtml` (פונקציה טהורה,
נבדקת ישירות ב-`paymentRequestDoc.test.ts`) בונה HTML מלא כולל טבלת עובדים
(`rows.map` דינמי) ושורת סה"כ; `generatePaymentRequestDoc` מעלה אותו ל-Drive עם
`drive.files.create` ו-`mimeType: 'application/vnd.google-apps.document'` - Drive
ממיר אוטומטית ל-Google Doc אמיתי כולל הטבלה. **אין Docs API ואין טמפלייט קבוע** -
כל לחיצה על "סיום דיווח חודשי" יוצרת מסמך חדש מאפס (`files.update` לא תומך
בעדכון תוכן, רק מטא-דאטה). מנגנון "דריסה" (יצירת מסמך חדש ואז trash לישן לפי
`previousDocUrl`) בדרך כלל לא רץ - נעילת החודש המלאה חוסמת ניסיון "סיום" שני
רגיל לאותו חודש. הוא כן מתפעל תרחיש קצה אמיתי: אם הפקת המסמך הצליחה אבל
שמירת הקישורים/נעילת ה-checkbox נכשלה אחריה (כשל Airtable חד-פעמי), החודש
נשאר לא נעול ו-`previousDocUrl` כבר קיים מהניסיון הקודם - ניסיון "סיום" חוזר
מזהה זאת ודורס את המסמך הישן במקום ליצור כפילות.

לצד המסמך עצמו, כל חשבונית שצורפה לדיווח (`INVOICE_REPORT_FIELDS.invoiceDoc`)
מועלית **גם** כקובץ נפרד בתיקיית החודש (`חשבונית - {שם עובד}.{סיומת}`), וגם
ממוזגת ל-**PDF אחד מאוחד** יחד עם ה-Doc עצמו (מיוצא ל-PDF דרך `drive.files.export`)
באמצעות `pdf-lib`: קובצי PDF ממוזגים כעמודים נוספים, קובצי jpg/png מוטמעים
כעמוד מלא. כשל במיזוג קובץ בודד נרשם בלוג ומדולג, לא מפיל את כל ההפקה. שלושת
הקישורים (מסמך, תיקייה, PDF מאוחד) + מזהה הקובץ הגולמי (`mergedPdfFileId`) של
ה-PDF המאוחד נשמרים על כל שורות הדיווח של החודש (`saveDocUrlForMonth`).
המייל נשלח דרך `notifyPaymentRequestEmail` (`makeWebhook.ts`, webhook פעיל
`PAYMENT_REQUEST_EMAIL_WEBHOOK_URL`, עם default מוגדר כמו `SUBMIT_WEBHOOK_URL`)
עם payload באנגלית: `fileId` (מזהה ה-PDF המאוחד ב-Drive, לא קישור - Make שולף
אותו לפי זה), `email` (הכתובת שהוזנה טרי בסיום הדיווח), `institution`, `role`
(budgetRow.title), `month`, ו-`cc` (רשימת `MOSAD_FIELDS.paymentRequestCcEmails`
של המוסד). כשל בשליחה מוחזר כ-`emailError` ברור ב-UI, לא כשל שקט.

**מלכודת**: `drive.files.create` עם `media.body` צריך **stream**, לא `Buffer`
גולמי - `Readable.from(Buffer.from(bytes))` (מ-`node:stream`), אחרת קריסה
(`part.body.pipe is not a function`) בהעלאת קבצים בינאריים (חשבוניות/PDF
מאוחד). ה-HTML→Docs upload הרגיל לא נפגע מזה כי שם `media.body` הוא string.

שתי מלכודות אמיתיות: (1) ה-HTML→Docs converter של Drive **מתעלם מ-`dir="rtl"`**
לגבי סדר העמודות בטבלה - הן נבנות תמיד לפי הסדר הליניארי של קוד ה-HTML, לכן
העמודות נכתבות בקוד **בסדר הפוך** (העמודה שאמורה להופיע הכי מימין נכתבת אחרונה).
(2) auth הוא **OAuth2 כמשתמש Google אמיתי**, לא Service Account - ל-Service
Account רגיל אין מכסת אחסון עצמאית ב-Drive (0 בייט), ופתרונות כמו Shared Drive/
domain-wide delegation דורשים Google Workspace שאינו זמין לחשבון Gmail רגיל.
משתני סביבה: `GOOGLE_OAUTH_CLIENT_ID`/`_SECRET`/`_REFRESH_TOKEN` (הרשאה חד-פעמית),
`GOOGLE_PAYMENT_DEST_FOLDER_ID` (תיקיית יעד, בבעלות אותו חשבון). (3) לוגו "מיוחדים
בחינוך" בראש המסמך (`public/logo_meyuhadim.png`, מוטמע כ-`<img>` עם data URI) -
**חייב PNG, לא WebP**: נבדק בפועל שה-HTML→Docs converter מתעלם בשקט מ-`<img>`
מסוג `data:image/webp` (המסמך נוצר תקין, בלי שגיאה, אבל בלי תמונה כלל) - אומת
דרך ייצוא PDF וקריאה חזותית, לא רק בדיקת מבנה ה-HTML המקורי.

מבנה תיקיות: `{תיקיית יעד}/{שנת לימודים}/{שם מוסד}/{חודש}/{קבצים}` (המסמך,
קובצי החשבוניות הבודדים, וה-PDF המאוחד - כולם באותה תיקיית חודש). שלוש
תת-התיקיות נמצאות/נוצרות אוטומטית בכל הפקה (`findOrCreateFolder` בתוך
`paymentRequestDoc.ts`, חיפוש לפי שם תחת ה-parent הנכון לפני יצירה, כדי לא
לשכפל). שנת הלימודים נקראת
מטבלת Airtable חדשה `הגדרות מערכת` (`src/lib/settings.ts`, מפתח
`SETTINGS_KEYS.academicYear`) כדי שעדכון שנה בתחילת כל שנה"ל יהיה עריכת ערך
ב-Airtable בלבד, בלי שינוי קוד. שם הקובץ: `{MM.YY של חודש הדיווח} - בקשת תשלום
חשבוניות - הדרכות פרא {שם המוסד}` ("הדרכות פרא" הוא טקסט קבוע, זהה בכל מסמך).

#### העברת יתרות בין חודשים

`src/lib/invoice/monthlyBalance.ts`. שעות **וגם תקציב (₪)** שלא נוצלו במכסה
החודשית המשותפת (ברמת שורת התקציב, לא פר-עובד) עוברים לחודשי הדיווח הבאים -
שני מסלולים עצמאיים לגמרי (שעות ותקציב לא נעים בהכרח באותו יחס, כי כל עובד
יכול לדווח בתעריף שונה), בכפוף לשני כללים שאושרו עם המשתמשת:

1. **חודש שדולג (מעולם לא ננעל) לא תורם את המכסה/התקציב המלאים שלו לשרשרת** -
   רק היתרה שכבר הצטברה *לפניו* ממשיכה לזלוג הלאה. למשל: ינואר ננעל עם יתרת
   שעות 20, פברואר מעולם לא דווח/ננעל, מרץ מקבל 20 (מינואר) - **לא** 20+50
   (יתרת ינואר + מכסת פברואר המלאה).
2. הבדיקה החיה (`checkLiveMonthlyQuota`) חוסמת רק כשסה"כ השעות/התשלום (₪)
   המדווחים בחודש חורגים מ-**מכסה/תעריף חודשי + יתרה נכנסת**, לא מהמכסה/
   התעריף הרגילים בלבד - כך שמותר לדווח יותר מ"הרגיל" אם יש יתרה זמינה
   שמכסה אותה (בשעות ובתקציב בנפרד).

**מימוש**: טבלת Airtable חדשה `יתרות חודשיות חשבונית` (ראו למטה) - שורה אחת
לכל שורת-תקציב+חודש, עם שני זוגות שדות מקבילים (שעות: מכסה סנאפשוט/יתרה
נכנסת/סה"כ מדווחות/יתרה יוצאת; תקציב: תעריף סנאפשוט/יתרת תקציב נכנסת/סה"כ
שולם/יתרת תקציב יוצאת - שני שדות ה"יוצאת" הם formula). נוצרת/מתעדכנת **רק**
בעת נעילת חודש (`finalizeMonthBalance`, נקרא ב-`finish-report/route.ts`
**לפני** `markMonthFinished` - אם זה נכשל, החודש לא ננעל, בדיוק כמו כל שלב
אחר בשרשרת ההפקה, כדי שלעולם לא יהיה חודש נעול בלי שורת יתרה תואמת).
"יתרה/יתרת תקציב נכנסת" = הערכים היוצאים (formula) של שורת היתרה הכי אחרונה
של אותה שורת תקציב עם חודש קטן מהמבוקש (`getCarryIn`, מחזיר `{hours, budget}` -
מדלג אוטומטית על חודשים מדולגים, כי להם פשוט אין שורה בטבלה בכלל).
`checkLiveMonthlyQuota` (`budgetCheck.ts`) קורא ל-`getCarryIn` ובודק את שני
הסוגים בנפרד (עצמאית - חריגה באחד לא תלויה בשני). `GET /api/invoice/reports`
מחזיר `carriedInBalance`/`carriedInBudget` - מוצגים ב-UI (`MonthlyReportScreen`)
בשני כרטיסי ה-KPI (המקסימום כולל את היתרה בכל אחד) וכהערה בכותרת כשיש יתרה
זמינה.
