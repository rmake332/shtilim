# עדכון מפת המערכת (שתילים)

הכלל מ-CLAUDE.md: **בכל פעם שפיצ'ר חדש מושלם — לעדכן את `docs/system-overview.md`**
כך שימשיך לשקף את המערכת נכון. שינויים קטנים/פנימיים (תיקון באג נקודתי, רפקטור
בלי שינוי התנהגות, שינוי טקסט ב-UI) **לא** מצריכים עדכון.

## מתי לעדכן — טריגר

עדכן אם השינוי נגע באחד מאלה:
- **זרימת משתמש** — שלב חדש/שונה באשף, מסך חדש בפורטל, מודול חדש.
- **טבלת/שדה Airtable** — טבלה חדשה, שדה חדש, שינוי משמעות שדה, dual-write.
- **לוגיקת חישוב מרכזית** — אופק, ניצול שעות, תקציב, תקרת שעות, משרת אם, פרא.
- **מודול בפורטל / API route חדש** או שינוי חוזה של route קיים.
- **אבטחה / קאשינג / משתנה סביבה** חדש.

אם כלום מאלה — כנראה לא צריך עדכון; ציין זאת קצרות וסיים.

## תהליך

1. **מפה את הדלתא של הפיצ'ר.** מה השתנה בפועל (לא מה שדובר עליו):
   ```bash
   git diff main...HEAD --stat
   git log main..HEAD --oneline
   ```
   שים לב לקבצים תחת `src/components/steps/`, `src/app/api/`, `src/lib/schedule/`,
   `src/lib/airtable/schema.ts` — אלה בד"כ מסמנים שינוי שדורש עדכון.

2. **אתר את הסעיפים המושפעים במסמך.** מבנה `docs/system-overview.md`:

   | סעיף | מתי לגעת |
   |------|----------|
   | `## מה המערכת עושה` | שינוי היקף/מטרה |
   | `## Stack טכני` | תלות/טכנולוגיה חדשה |
   | `## זרימת המשתמש` → `### פורטל`, `### אשף`, `### תיקון תת-תפקיד`, `### מודול תקני חשבונית` | כל שינוי בזרימה/מסכים |
   | `## Airtable` | טבלה/שדה |
   | `## לוגיקת ליבה` | חישוב מרכזי |
   | `## אבטחה` / `## קאשינג ורענון` | הגנות/רענון |
   | `## משתני סביבה` | env חדש (וגם `.env.example`!) |
   | `## מפת קבצים מהירה` | קובץ/מודול חדש משמעותי |

3. **הכן עדכון ממוקד.** ערוך רק את הסעיפים שהתיישנו — אל תכתוב מחדש את המסמך.
   שמור על הסגנון הקיים (עברית, כותרות, טבלאות, הפניות לקבצים ב-backticks).
   שדות Airtable — צלב מול `src/lib/airtable/schema.ts` (מקור האמת) כדי לא להמציא
   מזהים; במידת הצורך השתמש בסקיל `airtable-schema`.

4. **הצג לפני commit.** הראה למשתמש את ה-diff של המסמך (`git diff docs/system-overview.md`)
   ותן לו לאשר, לפני שזה נכנס ל-commit הסוגר של הפיצ'ר.

## עיקרון

המסמך הוא נכס תחזוקה, לא ארכיון. עדכון קטן ומדויק ששומר אותו נכון שווה יותר
ממסמך ארוך שהתיישן. אם סעיף כבר לא מדויק בגלל הפיצ'ר — תקן אותו; אם נוסף רכיב
שאין לו בית — הוסף פסקה קצרה במקום הנכון.
